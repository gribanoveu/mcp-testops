# AGENTS.md — правила для агента, который пишет MCP-сервер

Задача — MCP-сервер для **Allure TestOps** Альфа-Банка. Документы в `docs/` — аналитика,
написанная до тебя: источник фактов о контракте, но сверяйся с `openapi/api-docs.json`, если
что-то не сходится.

## Где ведётся работа

Всё делается **в этой папке** (`testops-mcp/`): здесь лежит аналитика (`docs/`), здесь же появляется код,
тесты и проектные файлы, и коммит идёт в репозиторий, в котором эта папка лежит. Никакого внешнего
репозитория в работе нет.

Единственный внешний след — `reference/`: фрагменты `MMBMB/mcp-testops` (HEAD `ad9c4daa`, снято
2026-11-09), сохранённые **как пример**. Это снимок для чтения, а не место работы: туда не ходить,
ничего туда не пушить, на его актуальность не рассчитывать — он может устареть и исчезнуть.

Соответственно:

- проект поднимается с нуля здесь, по `docs/03-tools-spec.md`;
- `docs/04-current-implementation.md` — разбор примера: какие решения там приняты и какие из них ошибочны
  (Д1–Д11). Читать как «чего не делать», а не как «список правок»;
- `reference/skeleton-excerpt.md` — код примера с номерами строк, на который ссылается `04`.

## Каркас проекта (в этой папке)

Создай его рядом с документами, ничего из этой папки не удаляя и не перенося:

```
testops-mcp/
├── README.md                 # этот указатель; затем — README самого проекта
├── CHANGELOG.md              # строка на этап: что сделано и когда
├── docs/01-contract.md … 06-open-questions.md   # аналитика, остаётся на месте
├── openapi/api-docs.json     # снимок спеки — вход для контрактных тестов
├── reference/                # пример из чужого репозитория (только чтение)
├── pyproject.toml            # hatchling; packages = ["src/mcp_testops"]; deps: mcp>=2,<3 (v2) или mcp>=1.0,<2 (v1), httpx>=0.27
├── tests/
│   ├── test_contract.py      # тела запросов валидируются схемами
│   ├── test_client.py        # httpx.MockTransport: пагинация, oneOf, 202/204, ошибки
│   └── test_tool_guards.py   # project_id, TESTOPS_READ_ONLY, отсутствие generic-инструмента
└── src/mcp_testops/
    ├── __init__.py           # сервер SDK + инструменты, по функции на инструмент
    └── __main__.py           # from . import main; main()
```

Коммиты — в тот репозиторий, где лежит эта папка, по одной теме на коммит.

Установка и запуск:

```bash
python -m venv .venv && . .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e .
python -m mcp_testops                          # stdio MCP, читает TESTOPS_* из env
```

Зависимости — только `mcp` и `httpx`; для тестов добавляй `pytest` и `jsonschema` в
`optional-dependencies`, не в рантайм.

## Стек: только официальный SDK MCP

Задача — писать на официально рекомендованных библиотеках MCP, поэтому:

- **SDK — только официальный Python SDK `mcp`** (github.com/modelcontextprotocol/python-sdk,
  документация `py.sdk.modelcontextprotocol.io`). Никаких сторонних обвязок — standalone `fastmcp`
  2.x/3.x от Prefect, `mcp-agent`, `fastmcp-slim`, самописный JSON-RPC по stdio. Совместимость
  с современными клиентами гарантирует только официальный SDK: он один обслуживает обе ревизии
  протокола сразу.
- **Актуальная линия — v2** (ревизия протокола 2026-07-28), для нового кода берём её:

  ```python
  from mcp.server import MCPServer          # в v1 было: from mcp.server.fastmcp import FastMCP

  mcp = MCPServer("testops")

  @mcp.tool()
  def list_projects(search: str = "") -> str:
      """List TestOps projects, optionally narrowed by a text search term."""
      ...

  if __name__ == "__main__":
      mcp.run()          # stdio по умолчанию; блокирует, пока живёт сервер
  ```

  В `pyproject.toml` — `mcp>=2,<3`. Для разработки ставится `pip install "mcp[cli]"`: экстра `cli`
  даёт команды `mcp dev` (Inspector на localhost:6274), `mcp run`, `mcp install`, `mcp version`.
- **Линия v1** (`from mcp.server.fastmcp import FastMCP`, `mcp>=1.0,<2`) поддерживается и остаётся
  допустимой, если продолжаешь готовую заготовку — она написана на ней. Переход на v2 механический:
  `FastMCP` → `MCPServer` из `mcp.server`, `mcp.server.fastmcp.*` → `mcp.server.mcpserver.*`,
  `ctx.fastmcp` → `ctx.mcp_server`, `FastMCPError` → `MCPServerError`, `get_context()` → параметр
  `ctx: Context`. Выбери одну линию и зафиксируй в `pyproject.toml`, чтобы импорты не разъезжались.
- **Транспорт — stdio.** Локальный MCP-клиент запускает сервер подпроцессом; `streamable-http` и SSE
  не нужны (SSE устарел), сетевое развёртывание — вне задачи.
- **HTTP-клиент к TestOps — `httpx`** (не часть SDK; stdlib `urllib` допустим, если нужен минимум
  зависимостей). Никаких `requests` и самописных ретраев поверх asyncio.

Проверка соответствия: `mcp version` показывает версию официального SDK, `grep -r "fastmcp" src/`
даёт только импорт SDK-пути (`mcp.server.fastmcp`) либо ничего (v2).

## Что уже решено за тебя

- Язык — **Python 3.10+**, MCP-сервер — на официальном SDK `mcp` (см. раздел выше), HTTP — **httpx**.
- Транспорт — **stdio**. Сервер запускается как `python -m mcp_testops` и не слушает портов.
- Всё, что зависит от стенда и проекта, приходит из **env**, а не из кода: один и тот же пакет должен
  подниматься под разные проекты (см. `docs/01-contract.md`, раздел «Конфигурация»).
- Набор инструментов и их сигнатуры — в `docs/03-tools-spec.md`. Не расширяй его «на будущее»: всего 634 пути
  в API закрываются 29 именованными инструментами; generic `api_request` сознательно не выводим
  (`docs/03-tools-spec.md` §7).

## Как писать код

1. **Одна функция = один инструмент.** `@mcp.tool()`, имя `snake_case`, глагол первым словом
   (`list_test_cases`, `create_launch`, `close_launch`).
2. **Docstring — это контракт для модели.** Первая строка — что делает, дальше — какие аргументы
   обязательны и в каком формате. Модель читает только docstring; если формат JSON-поля не описан,
   она его не угадает.
3. **Сложные объекты — JSON-строкой.** Инструменты MCP принимают примитивы и модели Pydantic; свободные
   вложенные структуры в них плохо переносятся, поэтому `tags_json`, `links_json`, `scenario_json`,
   `selection_json`, `custom_fields_json` принимаются строкой и разбираются через `_json_arg()`.
   Ошибку разбора возвращай текстом, не падай.
4. **Ошибки — данные, а не исключения.** Каждый инструмент ловит исключение и возвращает
   `{"ok": false, "error": "..."}`, как это сделано сейчас. Исключение внутри инструмента = потерянный
   турн агента.
5. **Ответ — компактный.** Не отдавай наружу `descriptionHtml`, `preconditionHtml`, `expectedResultHtml`,
   `postconditionHtml` — это HTML-дубли текстовых полей. Для `TestCaseDto` собери белый список полей.
6. **Один HTTP-клиент на процесс.** Сейчас `httpx.Client` создаётся на каждый вызов — переделай на
   модульный клиент с `timeout` из env. Заголовки запросов и токен не логируй.
7. **Пагинация — в одном месте.** Хелпер `_paged(path, params)` возвращает `content` и метаданные
   (`totalElements`, `totalPages`, `number`), не заставляя каждый инструмент повторять разбор.
8. **Мутации уважают `TESTOPS_READ_ONLY`.** Если флаг включён, write-инструменты не регистрируются
   (или сразу отвечают `{"ok": false, "error": "read-only mode"}`).

## Чего делать нельзя

- Хардкодить `TESTOPS_TOKEN`, `TEST_OPS_TOKEN` или любой другой секрет — в код, тесты, README, коммиты.
  README показывает `"TESTOPS_TOKEN": "****"`, реальное значение живёт только в локальном конфиге.
- Логировать заголовки запросов и тела ответов с персональными данными.
- Выводить инструменты для `/api/account*`, `/api/register`, `/api/mfa*`, `/api/globalsettings/mfa`,
  `/api/admin*`, `/api/email-verification*`, `/api/invite*`, `/api/login/invite-personal`,
  `/api/integration*` (в интеграциях лежат секреты) и для удаления проекта. Список — по фактическим
  путям снимка: `/api/registration` там нет, регистрация — `POST /api/register`.
- Возвращать generic-инструмент «любой путь под `/api`» (`api_request`) — ни за флагом, ни «только для
  GET»: денилист уже пропустил регистрацию (`/api/register`). Чего не хватает — добавляй именованный
  инструмент с телом из схемы, обоснование в `docs/03-tools-spec.md` §7.
- Делать инструмент «загрузить файл»: multipart через JSON-строку не собрать — для вложений и архивов
  нужен отдельный именованный инструмент.

## Как проверять

Минимум перед сдачей этапа:

```bash
python -m py_compile src/mcp_testops/*.py     # синтаксис
mcp version                                    # какая версия официального SDK стоит
mcp dev src/mcp_testops/__init__.py            # Inspector: список инструментов, ручной вызов
python -m mcp_testops                          # старт stdio-сервера, читает TESTOPS_* из env
```

`mcp dev` — самый быстрый способ проверить, что инструмент объявлен с нужной схемой аргументов:
Inspector показывает то, что увидит модель.

Плюс контрактные тесты (появляются в M1): каждое собранное телом тело инструмента валидируется схемой
из `openapi/api-docs.json`, каждый разобранный ответ — существующей схемой. Это ловит дефекты класса
«поле называется иначе» (именно так сломан `run_test_cases`).

Живой смоук — только на тестовом проекте, только чтение, кроме одного явно разрешённого сценария
«создать кейс → удалить с `force=true`».
